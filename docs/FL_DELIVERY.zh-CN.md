### 从R7到R8的部署差异

| 项目 | R7文件级部署 | R8整分区部署 |
|---|---|---|
| 写入方式 | 安装资源与模块，再通过helper原位激活视图库四个范围 | FileControl一次写入完整300 MiB `nflasha15` |
| 主机步骤 | install、activate，使用 `/setting` 事务日志 | deploy前备份完整分区，写一次，再完整回读 |
| helper | 上传临时 `libJit.so` 执行安装／激活 | 不上传helper |
| 旧日志与临时文件 | 会触发重复事务／占用保护 | 不读取或清理R7日志及临时载荷作为部署步骤 |
| `/setting` | 安装／激活事务及运行配置 | R8部署不写该分区，既有配置及日志保留 |
| WBI | R7未包含对应资源启动可见性核查 | R8不操作WBI，按用户指示暂缓该方向 |
| 实机新增文字 | 缺字／翻页串字 | 用户确认全部正常显示 |

R8复用此前实机成功菜单包的连接、认证与底层传输运行库。`transfer`、`read_to_file`、`load_rollback_session`、`same_camera`、`validate_partition` 五个函数经AST比较保持一致，运行库逐文件哈希一致。

## 部署与恢复操作

下列实机步骤由用户执行。每次命令从正常USB“大容量存储”模式开始，核对ILCE-9／6.00及物理端口后进入service mode。新包整分区部署不要求先执行R7的deactivate。

**已经完成R8部署且文字正常的机身，不需要为了当前9字节差异再次执行deploy。** 以下步骤用于复现、交接及明确需要时的恢复。

### 离线检查

```powershell
Set-Location '<固件分析目录>\a9_fl_full_partition_20261113_R8'
python -X utf8 .\service_tool.py --check
```

期望输出 `PASS_OFFLINE_PACKAGE_CHECK`，该命令不导入USB模块、不连接相机。

### 整分区写入

```powershell
python -X utf8 .\service_tool.py --deploy --confirm-write
```

工具先完整读取现场，持久化保存 `preimage.bin`，记录身份、长度、哈希及 `intent.json`，然后向 `/dev/nflasha15` 发送一次完整镜像。若现场已与目标一致则跳过写入。写后保存完整 `readback.bin`，长度和哈希都匹配才输出 `PASS_WRITE_READBACK`。

本包覆盖完整nflasha15，不自动合入候选之外的其他个人分区修改。写前备份是恢复到本次现场的依据。

### 冷启动与只读核验

即时回读通过后正常关机、断电再开机，使用简中或英语检查新增文字、参数、保存与效果。完整分区只读核验命令为：

```powershell
python -X utf8 .\service_tool.py --verify
```

读取文件保存在 `sessions\verify_时间_编号\readback.bin`。该工具比较整个分区的SHA-256，任何字节差异都会报告失败；不能仅凭这一条报错判断FL文件是否缺失，需分析保存的回读。当前已知R8现场属于下节记录的9字节元数据差异。

### 恢复到本次部署前

替换为实际部署会话目录：

```powershell
python -X utf8 .\service_tool.py --rollback '.\sessions\deploy_实际目录' --confirm-write
```

要求备份完整、哈希与intent匹配、机身身份一致。第一次写入即使中断、没有成功result.json，仍可使用满足这些条件的备份。恢复前也保存当前现场，写入仅发送一次并完整回读。

### 恢复到成功菜单基线

```powershell
python -X utf8 .\service_tool.py --restore-menu --confirm-write
```

该入口不依赖FL候选或某个部署会话，恢复包内成功菜单镜像，保留基线PP／SLog／比例及原创意风格功能，移除nflasha15中的本次FL修改。它不删除 `/setting` 中的配置与日志。

发生传输中断时保留整个会话目录，不自动重试、不删除日志后重跑。旧R7的recover／deactivate-recover不是R8整分区流程的替代命令。

## 本次实机证据

### R7：部分成功及缺字

R7 install会话 `install_20261113_213140_3afe8329` 完整核验通过。首次activate会话 `activate_20261113_213220_0408b4b8` 报 `GenericUsbException`，主机端最终报告、完整收尾及临时文件清理未闭环；随后回读的设备日志15条完整，最终phase100、cow15、written15。按绑定的载荷代码，phase100之前已通过视图库完整哈希校验并恢复只读挂载，不能将USB异常直接当作四段补丁未写完的证明。

第二次activate因已有事务日志停止，没有重复激活写入。普通deactivate因路径回读的视图库属于 `known-mixed` 而停止，未上传停用helper、未开始停用写入。

缺字后verify会话 `verify_20261113_220543_85770d35` 虽最终因临时 `libJit.so` 占用而停止，但此前完整文件回读已保存：两份语言文件均精确匹配旧版，视图库仅ELF头 `0x64/0x65/0x68/0x69` 四字节与期望不同，其余代码补丁正确。用户同时观察到翻页时沿用相邻页同位置文字、从取景页进入后文字为空。

这些证据确认了R7当时路径回读的资源不含新增文字；尚不能据此确定造成旧内容再次可见的底层机制。该历史问题不再作为R8文字仍缺失的现状描述。

### R8：文字通过，9字节元数据差异

部署会话：`deploy_20261113_225123_84b3a76f`。写入确已发送，完整即时回读与目标逐字节一致。

后续核验会话：`verify_20261113_225410_267ef618`。完整回读314572800字节，与部署会话机身身份一致。其SHA-256为：

```text
274026fe8c8813768d295d75ebeda10a6de8ac22a654cf9b2e9db58b03dedddc
```

与目标仅9字节不同，集中于1KiB块1、块2。这两个块整体匹配部署前像；其他分区字节匹配目标。所有文件内容、目录项及逐项比较的inode、mode、size与目标一致，原R7视图库ELF头四字节差异也已消失。

| 字段 | 镜像偏移 | 目标值 | 当前回读值 |
|---|---|---:|---:|
| 超级块空闲块计数 | `0x40c` | 9793 | 9832 |
| 超级块空闲inode计数 | `0x410` | 53322 | 53323 |
| 超级块最后写入时间 | `0x430` | 1794573179 | 1568315842 |
| 第23组空闲块计数 | `0xaec` | 2780 | 2819 |
| 第23组空闲inode计数 | `0xaee` | 1527 | 1528 |

只读 `e2fsck -fn` 对原目标镜像返回0，对当前回读返回4，明确报告空闲计数比位图多39个块、1个inode。这是实际的元数据一致性问题，不能仅按普通时间戳变化忽略。它不等于当前有39个文件块内容丢失：完整分区及文件审计已确认功能文件全部匹配。

用户在此后明确确认新增文字“全部正常显示”。因此，当前验收结论是：**整分区方案解决了实机新增文字缺失；文件系统汇总计数不一致仍保留，尚未执行修复。** 哪个阶段使这两个元数据块出现旧内容，仍未证明。

## 离线验证与未决事项

已完成以下验证，均由助手离线执行：

- 目标镜像ext2检查返回0，debugfs独立提取目标文件哈希一致。
- 完整文件系统树884项与成功菜单基线对照，确认修改范围。
- 精确R7模块、视图库、两份资源绑定；原厂ARM资源解析器91479项检查通过。这证明资源内容和解析，不替代实机LCD验收。
- 17项主机离线测试及300 MiB模拟写入中断、备份加载和回滚测试通过。
- Windows离线检查及普通主机权限下17项测试通过；压缩包CRC、513成员、解压文件哈希和禁止USB导入的offline检查通过。
